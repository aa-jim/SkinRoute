### Aspirants: already-owned passes were credited to premium-supply windows (Sep 30 2026)

### Aspirants: global reconciliation front-loaded every pack onto one day (Sep 28 2026)
- **Problem (user report, screenshot)**: over-recharge was fixed, but a plan that bought on three days now told the user to buy 2,510 BDT of packs on **one** — day 10/23, the phase-2 start. `aspirants_2026` dia-1,000 put `565+565+257` on day 10; `aspirants_5.0` dia-1,000 put its whole pool on day 15.
- **Root cause (not a pricing trade-off)**: which day a pack lands on is a pure **tie-break** — every assignment drawn from the candidate pool costs identical BDT, so the shape of the split is free. It collapsed anyway for two incidental reasons: the backtracking tried **anchor 0 first for every pack**, so "everything on the earliest day" was the first solution it emitted, and front-loading is the *easiest* assignment to validate (money that arrives early can never starve and never slips a tier). First-valid-wins therefore always picked the concentrated one.
- **Fix**: order each pack's candidate days **best-fit against what that day originally bought** (`|assignedDia + pack.dia − anchors[day].dia|`), then **simulate the floor-feasible solutions in order of how closely each preserves the original per-day split** (`Σ |assigned − original|`). The concentrated assignment is kept as an explicit **last resort**, appended after the sort, so a spread that fails validation costs the shape and never the price win. `MAX_SOLUTIONS` 24 → 48.
- **Report (verified)**: `verify:aspirants` **PASS 288** + **6 byte-identical non-aspirants**; the `aspirants_2026` day-0 pin `1d6e11f317f6940d` **held** (that cell already bought on three days). Prices are **byte-identical** — 2026 dia-1,000 stays ৳3,110, 5.0 dia-1,000 stays ৳2,938 / 1,940 dia — only the day split changes. `aspirants_2026` dia-1,000 now buys on days 10 and 15; `aspirants_5.0` dia-1,000 on days 8/15/19/20. Grid waste median **5 dia**, total 23,475. `next lint` (3 pre-existing `<img>` warnings) + `next build` (exit 0).
- Rule worth keeping: **a tie-break must never be decided by enumeration order.** The `docs/architecture.md` note now says so under the reconciliation bullet.

### Day-1 weekly pass dropped without a surprise window; pass yield is no longer a flat 220 (Sep 28 2026)
- **Problem A (user request)**: Aspirants plans bought a **pre-phase (day-1) weekly pass** on an event that has **no surprise tasks**. The day-1 unit only ever existed to bank recharge credit inside the `surprise_tasks.active_days` window (only claimable in the first few days); with no window there is nothing to bank it for, and on `aspirants_5.0` the first premium-supply phase is day 8, so the day-1 pass's own drip never matured in time to be used.
- **Fix A**: the drop-candidate search now treats it as a **hard rule, not a price question** — `!event.has_surprise_tasks` adopts the cheapest `dropMode: true` candidate **unconditionally**. Two traps found while wiring it: (1) `dropCandidates` mixes `dropMode: true` (removes the day-1 pass) with `dropMode: false` (merely buys fewer passes) — picking the globally cheapest one **re-added** the day-1 pass, so the `true` candidate is selected explicitly; (2) the **tier-pacing guard rejected every drop candidate** (dropping the pass reduces `preAccDraws`, which is what the guard measures), so the rule could never fire — `evaluateCandidate` takes `relaxPacing`, set only for the no-surprise case. Events **with** a surprise window (SF/JJK, `active_days: 3`) keep the ±30 BDT tolerance *and* the strict guard, and are byte-pinned unchanged.
- **Problem B (over-recharge)**: `buildItemList` valued every pass at a flat **220** (80 instant + 20×7). That is only true of a pass bought on day 1 with an empty drip queue — passes drip **sequentially** and a drip past `duration_days` is never received, so a pass bought on day 15 of a 23-day event is worth **80**. The flat 220 made the marginal pass look like 1.1 dia/BDT when it is really 0.4 (worse than any regular pack, ~0.55), so the knapsack over-bought. `buildItemList`/`optimizeRecharge` take an optional `passDiaValue` (the caller's real in-window yield via `passPurchasesTotalDia`); omitted → flat 220. **Recharge mode is untouched**: its weight stays `recharge_task_value` (100), credited on the purchase day regardless of drip.
- **Problem C (found by the new verifier check, not by hand)**: `passQueueEndDay` claimed to mirror `buildPassDripSchedule` but modelled passes as dripping **in parallel** from their own purchase day (`day + 6`) while the drip schedule chains one sequential cursor. A starved-day top-up pass appended to an already-overrunning queue was therefore credited a full 7-day drip it could never receive — one cell booked **1,580 dia of passes it only received 1,140 of** (30 grid cells failed). `passQueueEndDay` is now the same sequential-cursor loop, and a top-up pass is booked by its exact **marginal** yield (`passPurchasesTotalDia(withCandidate) − passPurchasesTotalDia(without)`), so the recharge summary, the simulator and the displayed schedule cannot disagree.
- **Report (verified)**: `verify:aspirants` **PASS 288** (144 × 2 editions, 60 draws, 0 warnings, funded, monotonic tiers) + **6 byte-identical non-aspirants**. No day-1 pass at any dia level on either edition; SF/JJK still print theirs (`Buy 3×/5× weekly pass` on day 1). Reference plan `aspirants_2026` dia-0 ৳3,610 → **৳3,487** and is now funded to the dia (3,150 bought = 3,150 spent, **0 left**, was 111 stranded). The reported case (`aspirants_5.0`, dia 0, all FP claimed) ৳5,535 → **৳5,271**, overshoot 525 → **213 dia**. `next lint` (3 pre-existing `<img>` warnings) + `next build` (exit 0); deterministic across repeated runs.
- **New verifier checks**: (12b) no pre-phase pass when the event has no surprise tasks; (13) the plan's `weekly_pass` row is an integer, ≤ `count × 220`, credits `recharge_task_value` per unit, and **replays to the same total** when the drip is recomputed from the schedule's own purchase notes. The regression block now also prints SF/JJK's retained day-1 pass so a leak out of the `has_surprise_tasks` guard reads as the cause, not a moved hash. Pin re-pinned `34a1d2dc3e1ee07a` → `1d6e11f317f6940d` with full rationale in-file.
- Docs: `docs/architecture.md` (pass valuation, one-drip-model rule, day-1 hard rule under Surprise tasks).
